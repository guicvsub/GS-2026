1. O que este componente entrega

O componente Dados é um pipeline orquestrado no Apache Airflow que leva o GTFS oficial da SPTrans do arquivo bruto até tabelas prontas no MySQL, consumidas pelo MVP em três momentos do uso: reconhecer o ônibus que chegou (vocabulário de letreiros para o OCR), orientar a viagem (sequência de paradas para o alerta de descida) e estimar a espera quando não há dado em tempo real (frequência por faixa horária). Um segundo DAG transforma os eventos de reconhecimento gravados pelo app em indicadores de impacto.

{{KPIS}}

A execução é repetível e idempotente: cada versão do feed é identificada pelo SHA-256; rodar de novo com a mesma versão não recarrega nada, e uma versão nova substitui a anterior em uma única transação.

Decisões técnicas

DecisãoJustificativa
Airflow 2.10.5, LocalExecutor, Docker ComposeAtende à orquestração pedida no enunciado com o menor número de serviços (sem Celery/Redis). Os DAGs só orquestram; a lógica fica no pacote pipeline/, testável sem Airflow.
ETL em Python/pandasVolume pequeno (≈165 mil linhas por carga, <20 s): cabe em memória; Spark seria custo sem ganho. A arquitetura em camadas permite trocar o motor se o volume crescer (ex.: várias cidades).
Short-circuit por SHA-256Evita recarga e versões duplicadas; registra a execução como ignorada em carga_controle.
Carga full-refresh transacionalO GTFS é publicado como foto completa. Apagar e inserir dentro de uma transação, com reconciliação de contagem, garante que o app nunca leia uma carga pela metade.
Portão de qualidade antes da cargaFalha crítica interrompe o DAG e preserva a última versão boa no banco.
Uma viagem de referência por linha e sentidoA SPTrans publica uma viagem por sentido e modela horários em frequencies.txt; o itinerário vem dessa viagem e a espera vem da frequência.
shapes.txt só no raw60 MB de traçado que o app não usa; o alerta de descida depende da sequência de paradas.

8. Segurança, LGPD e limitações

  • Credenciais fora do código: .env (no .gitignore) e GitHub Secrets. MySQL exposto só em 127.0.0.1.
  • Dados pessoais: o pipeline não recebe nenhum. evento_reconhecimento não tem imagem, coordenada, nome ou telefone; a sessão é um hash SHA-256 de um ID efêmero gerado no aparelho. As imagens são processadas no celular e descartadas.
  • IA responsável: o casamento OCR → letreiro marca ambiguo quando dois letreiros empatam (caso real: 8000-1 e 8000-10 vão para o mesmo destino). Nesse caso o app não confirma o ônibus.
  • Sem tempo real: a espera é estimada pela frequência planejada. Integrar a API Olho Vivo (posição dos ônibus) é o próximo passo.
  • Distância entre paradas é em linha reta: serve para antecipar o alerta de descida, não para navegação.
